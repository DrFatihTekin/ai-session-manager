# ai-session-manager: Product and Behavioral Specification

## 1. Purpose and specification boundary

`ai-session-manager` adds automatic, project-scoped session persistence to existing AI command-line tools. After one-time setup, users continue running their familiar tool commands. A wrapper selects a session, prints a short explanation, and launches the original tool with appropriate arguments.

This specification describes the current `0.1.9` application, using its source, tests, packaging metadata, and README as the reference. It is intended to let an independent team reproduce its functionality and command-line experience without copying its internal architecture.

Unless identified as a limitation or implementation detail, the behaviors below form the compatibility contract. Examples use representative paths and IDs; those values are dynamic. Native tools remain responsible for their interfaces, authentication, conversation content, and model behavior.

### In scope

- Install and remove wrappers around supported executables.
- Persist a separate session selection for each tool and project.
- Support both Git repositories and ordinary folders.
- Create managed session identifiers or discover native identifiers.
- Preserve explicit native session commands through bypass behavior.
- Inspect installation and state, reset session selection, and read older state formats.
- Work with Linux and Windows installations.

### Out of scope

- Gemini CLI support.
- Cross-tool session conversion, import, export, or conversation handoff.
- A graphical interface, background service, server, or remote session synchronization.
- Storing or editing conversation transcripts, model output, authentication, or credentials.
- Installing, repairing, authenticating, or updating the underlying AI tools.
- Providing a session browser, named-session management, or multiple managed sessions per tool within one project.

AGY's native storage happens to use a `.gemini` directory. Reading that directory for AGY is required and does not constitute Gemini CLI support.

## 2. Distribution and prerequisites

| Property | Contract |
|---|---|
| Distribution name | `ai-session-manager` |
| Management executable | `ai-session-manager` |
| Reference implementation | Python package `ai_session_manager` |
| Declared Python requirement | Python 3.8 or newer |
| Tested operating systems stated publicly | Linux and Windows |
| License | MIT |
| Runtime dependencies | Python standard library plus separately installed native tools |

Git is optional. Its absence must not prevent use in ordinary folders.

The reference distribution exposes `ai_session_manager.cli:main` as its console entry point. Its wrappers must be able to import `ai_session_manager.wrapper` using the Python interpreter they invoke.

Installation and removal:

```sh
pip install ai-session-manager
ai-session-manager setup

# Later, restore tool commands before removing the Python package:
ai-session-manager teardown
pip uninstall ai-session-manager
```

Editable development installation is also supported:

```sh
pip install --editable /path/to/ai-session-manager
```

**Required safety disclosure:** Setup renames installed CLI executables or launch shims and replaces their normal command paths with wrappers. Users must be warned about this and told how to restore originals with `teardown`. The containing directories must be writable. The application does not automatically elevate privileges.

macOS follows the Unix implementation, but must not be described as tested on the basis of the current documentation.

## 3. Supported tools and terminology

| Tool key and command | Display name | Session mode |
|---|---|---|
| `agy` | Antigravity CLI | `auto-resume` |
| `claude` | Claude Code | `managed-id` |
| `codex` | Codex | `auto-resume` |
| `copilot` | GitHub Copilot CLI | `managed-id` |

A **scope** is the project directory used to locate wrapper state. A **managed ID** is a UUID generated by this application. A **native ID** is an identifier generated by the underlying tool and discovered from its local records. The **real binary** is the original executable or shim retained beside the wrapper.

These are independent sessions: the four tools do not share conversation history or identifiers.

## 4. Management command interface

```text
ai-session-manager [--help]
ai-session-manager setup [tools...]
ai-session-manager teardown [tools...]
ai-session-manager status [tools...]
ai-session-manager reset [tools...]
```

The top-level description is:

```text
Manage per-project session persistence for AI CLI tools.
```

| Command | Help description |
|---|---|
| `setup` | Install wrappers for supported tools |
| `teardown` | Remove wrappers and restore original binaries |
| `status` | Show current installation state |
| `reset` | Delete persisted wrapper state |

### Tool selection and parsing

- Accepted tool arguments are `agy`, `claude`, `codex`, `copilot`, and `all`.
- No tool selection, or any selection containing `all`, means all four tools in alphabetical order: AGY, Claude, Codex, Copilot.
- Otherwise, process tools in supplied order. The reference does not deduplicate repeated names.
- Every subcommand accepts `-h` / `--help`.
- Invoking `ai-session-manager` without a subcommand prints top-level help and exits successfully.
- Invalid commands, tool names, or unsupported arguments use standard argument-parser errors and exit with status `2`.
- There is no application-level `--version` option or configuration-file option.

Examples:

```sh
ai-session-manager setup
ai-session-manager setup all
ai-session-manager setup claude codex
ai-session-manager status copilot
ai-session-manager reset agy
ai-session-manager teardown
```

Setup and teardown affect the executables found through `PATH`, not just the current project. Status includes current-project state. Reset affects only the current scope.

## 5. Setup lifecycle

For each selected tool:

1. Print `[<tool>]`.
2. Locate its normal executable using platform `PATH` lookup.
3. If missing, print `Skipping: '<tool>' not found in PATH.` and continue.
4. Compute absolute wrapper and real-binary paths without resolving the original executable's symlink target.
5. Inspect the wrapper path. The reference recognizes its wrappers by the text `ai_session_manager.wrapper` anywhere in the file; unreadable files are treated as non-wrappers.
6. Apply the following transition.

| Existing installation | Behavior |
|---|---|
| Normal executable, no backup | Rename executable to real-binary path; write wrapper |
| Wrapper and real binary both present | Report already installed; leave both unchanged |
| Wrapper present, real binary missing | Report broken installation; do not rewrite wrapper |
| Non-wrapper executable and real binary present | Treat as native tool reinstallation; replace old backup with current executable; reinstall wrapper |

Messages, excluding the tool header:

```text
Renamed <original-name> -> <real-name>
Wrapper installed at <wrapper-path>
```

Already installed:

```text
Already set up: real binary is <real-path>
Wrapper is at:  <wrapper-path>
```

Broken installation:

```text
Wrapper is active at <wrapper-path>, but <real-name> is missing. Repair or reinstall '<tool>' first.
```

Reinstallation detection:

```text
Detected <tool> was reinstalled — updating <real-name>.
Wrapper installed at <wrapper-path>
```

The original symlink or shim must be moved rather than moving its resolved target. For example, wrapping a symlink to an npm entry file must leave that target intact.

### Setup exit status

- Return `1` when no selected tool binary was found; also print `No supported tool binaries were found.`
- For explicitly named tools without `all`, a missing executable or wrapper with a missing backup makes the overall return status `1`, even if other selected tools succeed.
- In automatic/all-tools mode, those individual skips do not themselves make the result fail if at least one tool was found. A found but broken wrapper counts as found in the reference implementation.
- Otherwise return `0`.
- Permission and other filesystem failures are not converted into per-tool skips; see error behavior.

Setup neither creates project state nor repairs the native tool installation.

## 6. Installed wrapper mechanics

### Linux and other Unix platforms

If `PATH` resolves `<directory>/<tool>`, rename it to `<directory>/<tool>-real` and place this executable script at its former path:

```python
#!/usr/bin/env python3
# Auto-generated by ai-session-manager setup
from ai_session_manager.wrapper import run
run('<tool>')
```

The wrapper inherits the real binary's permission bits with user, group, and other executable bits enabled.

### Windows

Preserve the located executable's suffix for its backup. For example:

```text
copilot.exe -> copilot-real.exe
copilot.cmd -> copilot-real.cmd
```

The wrapper is always `<tool>.cmd` in that directory:

```bat
@echo off
set "AI_SESSION_MANAGER_REAL_BIN=%~dp0<real-name>"
set "AI_SESSION_MANAGER_TOOL=<tool>"
python -c "from ai_session_manager.wrapper import run; run()" %*
```

Argument forwarding therefore follows Windows command-shell semantics, rather than a custom quoting protocol.

### Runtime tool and executable resolution

Determine the tool from, in order:

1. An explicit tool key supplied by the generated Python wrapper.
2. `AI_SESSION_MANAGER_TOOL`, when nonempty.
3. The invoked script's filename stem.

Unknown keys raise `ValueError` with `Unsupported tool: <key>`.

Use `AI_SESSION_MANAGER_REAL_BIN` if it points to an existing executable. An invalid or stale override falls back to discovery.

Discovery checks a real-binary sibling of the resolved invoking script first. On Windows this sibling is derived from the script stem and suffix; on Unix it is `<tool>-real`. Then search `PATH`: Windows tries `<tool>-real.exe` and `<tool>-real` within each directory; Unix tries `<tool>-real`. Candidates must exist and be executable.

If none is found, raise a file-not-found error with:

```text
Cannot find '<tool>-real'. Run 'ai-session-manager setup <tool>' first.
```

## 7. Project scope and persistent state

Resolve the current working directory to an absolute, symlink-resolved path. Run:

```sh
git rev-parse --show-toplevel
```

If successful, use that repository root as the scope and classify it as `repo`. Otherwise, including when Git is unavailable, use the resolved current directory and classify it as `folder`.

Consequences:

- All subdirectories within one repository share wrapper state.
- Ordinary folders use their own state; there is no upward search for a parent's state directory.
- Sibling folders and different repositories have independent state.
- Branch changes do not create separate state.
- The scope name in launch messages is the scope directory's final path component.
- Scope resolution does not change the child tool's working directory; the tool still starts where the user invoked it.

Layout:

```text
<scope>/
  .ai-session-manager/
    agy.json
    claude.json
    codex.json
    copilot.json
```

Create directories and the selected tool's file lazily during a managed launch or migration. Do not require all four files.

### JSON format

Managed-ID example:

```json
{
  "version": 1,
  "tool": "claude",
  "session_mode": "managed-id",
  "resume_target": "123e4567-e89b-42d3-a456-426614174000"
}
```

Native-ID example before discovery:

```json
{
  "version": 1,
  "tool": "codex",
  "session_mode": "auto-resume"
}
```

After discovery, include `"resume_target": "<native-id>"`.

New writes use the field order shown, two-space JSON indentation, and a final newline. The current tool registry, not a loaded `session_mode` field, determines launch strategy.

The state holds session selection only, not a transcript. It is local plaintext and is not encrypted. The application does not automatically edit a project's `.gitignore`.

### Legacy state precedence and migration

Load the first applicable source:

1. Current `.ai-session-manager/<tool>.json`.
2. In a repository, `.git/ai-session-manager/<tool>.json`.
3. For Copilot only, `.git/copilot-session` in a repository or `.copilot-session` in a plain folder.

For the old per-tool JSON, copy the parsed payload to the current location. For old Copilot text, trim whitespace and wrap a nonempty ID in the current Copilot schema. Empty Copilot text counts as no state.

Leave legacy files in place during migration. Do not consult a lower-precedence source if the current JSON exists but is malformed. The reference has no general schema-upgrade or schema-validation layer.

## 8. Native command bypass

Before reading, creating, or migrating project state, inspect the user arguments. A bypass forwards the original argument list unchanged to the real tool, without manager launch messages, state writes, or post-exit native-ID discovery.

All tools bypass for any argument matching:

```text
-h --help -V --version
```

| Tool | Additional bypass flags | Passthrough commands |
|---|---|---|
| `agy` | `-c`, `--continue`, `--conversation` | `auth` |
| `claude` | `-c`, `--continue`, `-r`, `--resume`, `--session-id` | `agents`, `attach`, `auth`, `install`, `update` |
| `codex` | None | `app`, `debug`, `exec`, `mcp`, `resume`, `review`, `sandbox` |
| `copilot` | `--session-id`, `--resume`, `--continue`, `--clear`, `-p`, `--prompt` | `update` |

For flags, compare the portion before the first `=`. Thus `--session-id=value` bypasses where `--session-id` is listed. Do not infer aliases, combined short options, or flags not listed above.

For passthrough commands, compare the first argument not starting with `-`; a lone `-` also counts as positional. Stop positional-command detection at `--`. This is a simple scan, not a complete native argument parser: an option value may be interpreted as the first positional argument. The separate bypass-flag scan still examines all arguments, including those after `--`.

Examples:

```sh
copilot --resume
copilot -p "Explain this project"
claude -r chosen-session
agy --conversation chosen-conversation
codex resume --last
codex review
```

Explicit native sessions do not replace the wrapper's saved selection.

## 9. Managed launch and resume lifecycle

For a non-bypassed invocation:

1. Resolve the real binary and scope.
2. Load or migrate state.
3. If absent, persist initial state before launching.
4. If present, discover or refresh a native target where applicable.
5. Print the relevant launch message.
6. Prepend manager arguments to the original user arguments and launch the real tool.

Original user-argument order is preserved. The manager does not reinterpret prompts or tool output.

### Tool-specific arguments

`<args>` below means the original user arguments:

| Tool | First managed invocation | Subsequent invocation with usable ID | Fallback without usable exact ID |
|---|---|---|---|
| Copilot | `--session-id <generated-uuid> <args>` | `--session-id <same-uuid> <args>` | No automatic native validation or fallback |
| Claude | `--session-id <generated-uuid> <args>` | `-r <saved-uuid> <args>` if native session file exists | `-c <args>` when saved session file is missing |
| Codex | `<args>` | `resume <native-id> <args>` | `resume --last <args>` on later launches |
| AGY | `<args>` | `--conversation <native-id> <args>` | `-c <args>` on later launches |

Generate managed IDs as UUID version 4 strings. Reuse them until reset; different tools receive independently generated IDs.

For AGY and Codex, an absent wrapper state always means a normal first launch, even if older native sessions already exist.

### Native target refresh

For existing AGY or Codex state:

- If `resume_target` is absent, attempt discovery and persist an ID if found.
- If an existing target fails the validation rules in section 10, rediscover.
- Replace it only if discovery returns a different ID.
- If discovery fails or returns the same rejected ID, persist marker-only state and use the native latest-session fallback.

After an AGY or Codex process exits with code `0`, attempt discovery again and save the selected ID if found. If discovery returns nothing, leave state as it stands. Do not perform this post-run update after a nonzero exit.

Initial state and pre-launch refreshes are not rolled back after launch failure.

### User-visible launch messages

Print one of these to standard output, flushed before process launch:

```text
[ai-session-manager] New session <id> (<scope-name>)
[ai-session-manager] Starting new Antigravity CLI session (<scope-name>)
[ai-session-manager] Starting new Codex session (<scope-name>)
[ai-session-manager] Resuming session <id> (<scope-name>)
[ai-session-manager] Resuming latest Antigravity CLI session (<scope-name>)
[ai-session-manager] Resuming latest Codex session (<scope-name>)
```

Claude first prints its normal `Resuming session` message when state exists. If its native session file is missing, it then prints:

```text
[ai-session-manager] Stored Claude session <id> is missing; falling back to Claude's latest-session resume.
```

That fallback does not change the saved Claude ID.

### Process behavior

- Preserve the user's working directory, environment, and interactive standard streams.
- On Unix, managed Claude/Copilot launches and all bypass launches replace the wrapper process using `exec` semantics.
- Managed AGY/Codex launches use an inherited-stdio subprocess on every platform so the wrapper can perform post-exit discovery.
- On Windows, other launches also use a subprocess and exit with its return code.
- Propagate the tool's normal exit status; do not capture its interactive output or create a synthetic successful result.
- No custom signal-forwarding or terminal-emulation layer is defined by the reference.

## 10. Native storage adapters

These adapters depend on native tools' local, potentially unstable file formats. They discover identifiers; they do not import conversations or verify that the native CLI can successfully resume them.

Home-directory paths below use the active user's home. Custom native storage-home environment variables are not interpreted by the current adapters.

### Claude session existence

Construct a project key from the resolved scope path by replacing each backslash, slash, and colon with a hyphen. The expected session file is:

```text
~/.claude/projects/<project-key>/<saved-id>.jsonl
```

Only check existence, not transcript contents. A missing file triggers the warning and `-c` fallback in section 9.

### Codex discovery and validation

1. Recursively inspect `~/.codex/sessions/**/*.jsonl`.
2. Read nonempty lines until a `session_meta` record is found.
3. Require its `payload` to be an object containing a string `id` and `cwd` exactly equal to the resolved scope path.
4. Require the ID to appear as `session_id` in a record in `~/.codex/history.jsonl`.
5. Select the eligible session with the greatest session-file modification time. The reference breaks equal-time ties by lexicographically greatest ID.

Skip unreadable session files. A malformed JSON line stops scanning that session file. Invalid JSON lines in history are skipped. Missing or unreadable history means no ID passes history validation.

A saved Codex ID is considered valid solely when it appears in history; validation does not additionally verify its workspace or transcript. Discovery does verify workspace as above.

### AGY discovery and validation

Read:

```text
~/.gemini/antigravity-cli/history.jsonl
```

Scan records from the end of the file, skipping blank lines, invalid JSON, and entries whose `workspace` differs from the resolved scope path.

- Return the first matching nonempty string `conversationId`.
- If a matching entry instead has a nonempty string `display`, trim it and stop scanning older entries. Use this prompt for the transcript fallback.
- If neither is available, continue searching older matching entries.

For the transcript fallback, inspect:

```text
~/.gemini/antigravity-cli/brain/<conversation-id>/
  .system_generated/logs/transcript_full.jsonl
```

Use `transcript.jsonl` only if `transcript_full.jsonl` is absent. Inspect brain entries in descending directory modification-time order.

For each transcript, skip blank/invalid JSON lines and find the first record with `type` equal to `USER_INPUT`. From its string `content`, extract and trim text between the first `<USER_REQUEST>` and `</USER_REQUEST>` tags. Do not search later user-input records if the first has no extractable request.

Return the directory name of the first transcript whose extracted request exactly equals the saved history `display`. Missing or unreadable relevant files produce no discovery result.

A saved AGY ID is considered valid only if a history record contains both that `conversationId` and the matching `workspace`. A transcript-only match is not itself sufficient for this validation.

File order and filesystem modification time, not history timestamp fields, determine recency in these algorithms.

## 11. Status command

For each selected tool, print this block with a blank line between tools:

```text
Tool         : <tool>
Platform     : <platform-name>
Binary       : <located-path-or-not found>
Real binary  : <located-backup-path-or-not found>
State file   : <absolute-current-state-path>
State        : <present-or-missing>
Status       : <wrapper active-or-real binary-or-not installed>
```

The platform name is the system platform name, such as `Linux` or `Windows`. Binary fields use `PATH` lookup. `State` tests existence only; it does not parse, migrate, or validate state.

If a normal command exists, inspect its wrapper path for the wrapper marker and report `wrapper active` or `real binary`; otherwise report `not installed`. The reference resolves the located binary path before this status inspection, unlike setup's symlink-preserving path handling.

Status returns `0`, including when tools are not installed. It does not confirm that an active wrapper has a working real binary or a resumable native session.

## 12. Reset command

For each selected tool, print `[<tool>]` and remove:

- Its current scoped `.ai-session-manager/<tool>.json`, if present.
- Its legacy repository `.git/ai-session-manager/<tool>.json`, if applicable and present.
- For Copilot, the applicable legacy text file, if present.

For each removed file, print:

```text
Removed: <path>
```

If anything was removed, print:

```text
Next '<tool>' in this <repo-or-folder> will start fresh.
```

Otherwise print:

```text
No state file found for this <repo-or-folder>: <scope-path><legacy-hints>
```

Repository legacy hints append ` or migrated legacy <tool>.json`; Copilot additionally appends ` or legacy copilot-session` in repositories or ` or legacy .copilot-session` in folders.

Reset returns `0` when files are absent as well as when deletion succeeds. It leaves state directories and native conversation files intact and does not alter wrappers.

The next managed launch creates new wrapper state: a new UUID for Claude/Copilot or an ordinary native launch for AGY/Codex. This does not prevent the native tool from independently choosing to continue something.

## 13. Teardown command

For each selected tool:

1. Print `[<tool>]`.
2. Find the normal command and, separately, `<tool>-real` through `PATH`.
3. If neither exists, print `Skipping: neither '<tool>' nor '<tool>-real' found.` and continue.
4. Locate a backup alongside the normal command, or use the discovered backup.
5. Remove the wrapper if present, restore the backup to the original command name, and print `Restored <real-name> -> <original-name>`.

If no backup can be found for a located command, print:

```text
Nothing to undo: real binary not found alongside wrapper.
```

On Windows, consider the located path's suffix first, followed by `.exe`, `.cmd`, `.bat`, `.com`, and no suffix, without duplicate candidates. Preserve the selected real binary's suffix on restoration. In particular, `copilot.cmd` plus `copilot-real.exe` restores `copilot.exe`, not `copilot.cmd`.

If only a real binary is on `PATH`, teardown can restore it even when the normal command is missing.

Exit rules match setup's missing-tool selection rules: explicit missing selections cause `1`; automatic skips do not if any tool was found. If none was found, print `No supported tool binaries were found.` and return `1`. A found command without a backup is a no-op, not an explicit failure.

Teardown does not delete project state, native transcripts, or the Python package.

**Reference limitation:** Teardown does not require marker-based wrapper verification before removing the computed wrapper path when a backup exists. It is a restoration operation, not a general installation-integrity check.

## 14. End-to-end user journeys

### Familiar command, persistent conversation

```text
$ ai-session-manager setup copilot
[copilot]
Renamed copilot -> copilot-real
Wrapper installed at /example/bin/copilot

$ cd /work/my-project
$ copilot
[ai-session-manager] New session <uuid> (my-project)
<native Copilot interface>

$ copilot
[ai-session-manager] Resuming session <same-uuid> (my-project)
<native Copilot interface>
```

Claude has the same manager messages but starts with `--session-id` and subsequently uses `-r`, subject to the native-file check.

### Native ID discovery

```text
$ codex
[ai-session-manager] Starting new Codex session (my-project)
<native Codex interface; successful exit; ID discovered>

$ codex
[ai-session-manager] Resuming session <native-id> (my-project)
<native Codex interface>
```

AGY follows the same journey with display name `Antigravity CLI` and exact resume arguments `--conversation <native-id>`.

### Explicit override, reset, and removal

```sh
claude -r another-session          # Native bypass; saved manager selection is unchanged.
ai-session-manager reset claude   # Remove only this scope's Claude selection.
claude                           # Create a new managed UUID.
ai-session-manager teardown claude
claude                           # Run restored native executable without manager behavior.
```

There are no manager confirmation prompts, setup wizard, or interactive menus. Interactive behavior after launch belongs to the underlying CLI.

## 15. Error handling and known compatibility limits

The following are current limitations, not additional promises or requests to reproduce defects:

- The reference does not catch general permission, rename, write, JSON-state parsing, or process-launch errors at its public boundary. Such failures can display a Python traceback and exit nonzero. No rollback, transactional setup, or automatic repair is provided.
- State writes are direct replacements, without locking or atomic temporary-file replacement. Concurrent launches or reset during an active tool process are not coordinated.
- Existing state is not schema-validated. Missing fields or invalid JSON shapes can fail at runtime. Marker-only historical Claude state is not fully upgraded to a managed UUID.
- A native tool reinstall may overwrite the wrapper. Rerunning setup restores wrapping, but no background monitor does so automatically.
- Moving a project retains its state if its state directory moves, but native workspace paths and Claude project-directory lookup may no longer match. Automatic relocation repair is not implemented.
- Shared repository state and inherited child working directory differ when launching from a subdirectory. Native sessions recorded under that subdirectory may not be discoverable using the repository-root scope; Claude's root-derived existence check may also miss them.
- Native latest-session fallbacks are delegated to the tools and are not guaranteed to select this project's intended conversation.
- Native IDs are validated heuristically, not by a successful resume operation. The wrapper does not retry if the underlying tool rejects one.
- An AGY transcript-discovered ID absent from history can be rejected on a later launch; rediscovery of that same rejected ID falls back to latest-session behavior.
- AGY transcript matching can be ambiguous when conversations begin with identical requests. Modification-time ordering is the only selection heuristic.
- Native JSONL readers expect object-shaped records and known storage formats. Their handling of missing files and malformed JSON does not make every possible storage corruption safe.
- Copilot IDs are not checked against native history. Claude's missing-file fallback retains the old saved ID rather than adopting the session actually resumed.
- Setup can partially modify an installation before an operating-system error. Windows shell lookup and script execution depend on the user's actual environment.
- Declared Python support and platform claims are not a guarantee of compatibility with every future native CLI release.

A replacement may improve robustness without changing ordinary UX, but any intentional behavioral differences should be documented rather than presented as existing functionality.

## 16. Acceptance criteria

Use isolated temporary directories and fake executables/native history to test filesystem and argument behavior without modifying real installations. Native interactive checks should be run separately on Linux and Windows.

| Scenario | Required observable result |
|---|---|
| Git root and nested working directory | State path is at repository root; tools retain invocation working directory |
| Plain folder with or without Git installed | State is under that folder's `.ai-session-manager` |
| Two projects or two tools | State selections remain independent |
| First and second Copilot launch | One UUID persisted; both launches receive the same `--session-id` |
| First Claude launch and existing native session on relaunch | Initial `--session-id`; subsequent `-r` with identical ID |
| Missing Claude native session file | Warning plus `-c`; saved ID unchanged |
| First AGY/Codex launch | No injected resume arguments; marker state written before launch |
| Successful AGY/Codex exit with discoverable ID | Native ID persisted; subsequent launch receives exact resume arguments |
| Nonzero AGY/Codex exit | Same exit code; no post-exit target update |
| Existing marker without discoverable native ID | Later launch uses latest-session fallback |
| Stale native target | Different discovered ID replaces it; absent/same rejected ID becomes marker-only state |
| AGY history lacks ID but prompt matches transcript | Matching brain directory name is discovered |
| Codex history omits an otherwise matching transcript ID | That transcript is not selected |
| Explicit native flags, commands, help, and version | Arguments forwarded unchanged; no manager message or state creation/update |
| `--flag=value` for a listed bypass flag | Same bypass as the bare flag |
| Current and legacy state both present | Current state wins |
| Legacy per-tool or Copilot state only | Current file created; ID preserved; old file retained |
| Setup repeated on a healthy wrapper | Reports already installed; executable unchanged |
| Setup of a symlink-based command | Link moved to backup; target untouched |
| Wrapper present but backup missing | Explicit setup returns `1` with repair guidance; wrapper not rewritten |
| Native executable reinstalled over wrapper | Setup replaces old backup and reinstalls wrapper |
| Windows `.cmd` wrapper plus `.exe` backup | Teardown restores `.exe` and removes wrapper |
| Invalid real-binary environment override | Normal real-binary discovery still works |
| Reset selected tool | Current and applicable legacy files removed; other tools and native histories untouched |
| Teardown followed by native launch | Original executable restored; no manager launch messages |
| Status with absent tools/state | Correct `not found`, `missing`, `not installed` fields; return `0` |
| Explicit unavailable tool versus automatic selection | Exit statuses follow sections 5 and 13 |

Assert both user-visible messages and the exact child argument arrays. Exercise subprocess return-code propagation and Unix replacement behavior separately. Do not treat unit tests or synthetic history fixtures as proof that all current native CLI versions accept the adapter arguments.

## 17. Reference implementation and release handoff

The current implementation separates management operations (`cli.py`) from runtime wrapping, scope/state handling, and native discovery (`wrapper.py`). An independent implementation may use a different structure while retaining the contracts above.

The reference test command, run from the repository root against source rather than an independently installed version, is:

```sh
PYTHONPATH=src pytest -q
```

Current build metadata uses `setuptools>=77` and `wheel`. The release workflow:

1. Starts on a published GitHub release or manual dispatch.
2. Checks that the selected revision is an ancestor of the fetched `main` revision.
3. Runs source tests on Python 3.8 and 3.12 using Ubuntu runners.
4. Builds source and wheel distributions on Python 3.12 with `python -m build`.
5. Checks distribution metadata using `python -m twine check dist/*`.
6. Uploads/downloads distribution artifacts and publishes to PyPI using trusted publishing with an OIDC token and the GitHub environment `pypi`.

The package metadata determines the published version; a Git tag alone does not change it. The current workflow does not provide a Windows test matrix, despite the project's documented Linux/Windows testing claim. Building with the modern backend is distinct from running source tests or installing a compatible wheel on Python 3.8.

Reproducing the application does not require reproducing the repository owner's publishing credentials or deployment environment. It does require a distributable installation whose management command and generated wrappers invoke the same runtime consistently.
